一、背景与目标

当时治理处在 L2：品鉴、观澜、清流等 Agent 各自独立，误判筛查、策略配置、实验设计、上线部署大量依赖人工，闭环成本高、效率低。项目组成立 4 人小团队推进自动化，去掉繁杂流程，把发现到上线的链路串起来。

链路目标：高曝光低质内容从发现 → 召回 → 归因 → 策略 → 镜像验证 → 实验 → 发布，形成可追踪闭环；人工只卡在阈值确认、策略方案审核、进实验确认、边界 case 决策等节点。

二、L2 → L3 治理体系演化

L2 是「教 AI 做事」：7 步人机协同，实验全程人工建号、配流量、看数据、决定推全。L3 目标是「让 AI 自己做」：压缩为 6 步，检测、归因、镜像 QA、AB 建实验、推全/回滚尽量自动化，策略 proposal 仍由人工审核。

三、整体架构与 Agent 链路

按简历落地口径，L3 Multi-Agent 编排为：

品鉴（发现）→ 回响（Embedding 召回）→ 观澜（归因分流）→ 定澜（策略 / AB）→ 云河（镜像 QA 上线）

对外汇报里的五步主链路（问题发现 → 相似召回 → 策略校验 → 策略配置 → 上线发布）与上面对应，核心约束是：镜像不过，不进实验。

各环节职责（摘自项目文档）

  • 问题发现 / 品鉴：高曝光巡检；标签状态前置（已有标签 / 库有未打 / 无标签）；输出标签 + weighttype；双大模型交叉验证。
  • 相似召回 / 回响：无标签或库有未打时触发；向量召回相似内容；多档阈值分段抽检，推荐阈值后需人工确认；达标后打 weighttype。
  • 策略校验 / 观澜·定澜：weighttype 查 tag 映射，复用存量线上策略或新建方案；输出处置结论 + 策略方案（手段、参数、实验设计）。
  • 策略配置 / 云河：配置落地 → 镜像功能验证 → 人工确认后调实验接口建实验。
  • 上线发布：观察 ≥3 天；达标扩量推全；不达标分型路由；记录 case 状态。
人工卡点固定在：阈值确认 · 策略方案审核 · 进实验确认 · 边界 case 决策。

四、关键产品决策：无标签 badcase 怎么治

传统路径是对 badcase 打标再配策略。打标依赖内容理解团队，周期长、人工成本高，撑不起 Loop 自迭代。项目里对无标签问题改走 Embedding 相似召回，输出规则–weight–标签映射，用 weighttype 降权覆盖。

典型 case：机票类营销笔记（封面/标题强营销感），线上无对应三级标签，无法直接配策略。探查用 9 条 seed 做文本 embedding 召回。
治理口径阈值 ≥0.82阈值 ≥0.84
宽口径（封面+标题营销感） 94 条候选，准确率 85.1% 30 条，准确率 100%
窄口径（正文也为站内营销） 准确率 49.5%，不能直接用 样本过少，不推荐
主要误伤 标题像营销、正文实际是攻略/资讯（「宽是窄否」）

当时拍板的取舍

  • 不做「等内容理解建标签 + 逐条打标」——周期以周计，跟不上 loop。
  • 改用 embedding 召回 + 打 weighttype，再查映射复用存量策略，把周期压到天级。
  • 阈值不能全自动：分段抽检只能估准确率，误伤清不掉，最终阈值必须人工确认。
  • 口径先定：宽/窄口径不定，阈值没有意义；一期先按宽口径降权。

回响 Agent 在 Dify 上从 0 到 1 搭工作流：seed → 向量召回 → 多档阈值评测 → 打 weighttype；并协同研发打通各 Agent 之间的链路，记录 case 与 loop 中间过程，反哺后续迭代。

验证原则（项目内约定）

  • 镜像 QA：进实验前的配置与功能检查；镜像不过，绝不进 AB。
  • AB 实验：小流量效果验证；不达标不等于失败，先分型再路由（调参、回归因、延长观察、回滚、人工）。
  • Case / Loop 台账：记录每个 case 生命周期与每轮漏斗（发现量 / 处理量 / 失败量 / 卡点），用于定位失败原因。

六、我在项目里具体做了什么

岗位：AI 产品经理（信息流策略）。主要负责体验治理分支的方案与推进。

方案设计
参与 L2→L3 演化路径与 Multi-Agent 编排设计（品鉴 → 回响 → 观澜 → 定澜 → 云河）；明确人工卡点与「镜像不过不进 AB」；整理 Case / Loop 过程记录要求。
关键决策
针对无标签 badcase，推动 Embedding 相似召回 + weighttype 降权，替代长周期打标路径；参与宽/窄口径与阈值人工确认规则的落地。
原型与协作
在 Dify 0-1 搭建回响工作流；协同研发打通 Agent 链路与 Embedding 部署相关事项；跟进实验与上线节奏；持续发现 Top 内容 badcase，按问题严重性推动重排/降权策略。
结果
多轮 loop 后，首页信息流 Top 内容 badcase 率从约 10% 降至 1.5%（目标 2%）。
